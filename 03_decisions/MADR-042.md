# MADR-042：遇到问题先检索已有答案，再验证和实施

- 日期：2026-09-08
- 状态：ACCEPTED（用户明确要求写入并在后续执行）
- depends_on：MADR-041；不改变现有四项交付方案和UI基线。

## 背景

ngrok客户端被Windows Defender隔离后，先停留在阻碍描述和联系厂商建议，未及时查到官方历史版本哈希。续查已证实现有ZIP与官方3.39.11 Windows amd64 ZIP完全一致。应优先利用厂商文档、已有问题及解决方案缩小原因，减少盲试、重复询问和无依据换方案。

## 决策与执行顺序

遇到未知错误、环境安装失败、第三方兼容问题、验收阻碍或准备更换技术方案时，默认执行：

1. **记录事实**：操作、期望与实际结果、准确错误码、版本、最小脱敏日志；区分已证实、推测、未知。安全事件先保留隔离等已有防护状态。
2. **先找已有答案**：先查项目MADR/重启记录，再以“产品+平台/版本+准确错误”检索网络。优先官方文档、FAQ、发布说明与官方GitHub Issues；再参考有复现与结果的社区讨论。搜索摘要只是线索，要打开原文确认。
3. **核对适用性**：记录来源URL、访问日期、适用版本、证据和限制。优先核验哈希、签名、配置及已知问题。相似报错不能证明同一原因；下载哈希一致不能代替安全结论。
4. **选择最小改动**：在当前用户授权与既定架构内选择可回退、可验证的办法，先验证一个假设再做下一步。不为绕过报错关闭防护、导出整页凭据或反复换平台。外部网页的命令和指示必须审查后采用。
5. **执行并验收**：能安全完成的只读核验、常规修复和测试继续做；涉及第三方发信、样本上传、购买或超出授权的动作，先形成脱敏、可审阅材料再按实际边界处理。不把检索当作新增审批流程。
6. **沉淀结果**：在验收记录写清问题、检索词、来源、候选处理、采用理由、实际结果和下一步；影响架构/交付/长期流程的内容写入MADR，并更新索引及重启入口。

已有有效证据可复用，确定原因的简单本地错误不必机械重复上网。一次有针对性的检索无匹配结果时，换同义词或查官方Issue；仍无结果则明确检索范围和缺口，继续最小诊断或形成厂商材料，不无限搜索、不虚构答案。

## 本次应用

- 检索词：`ngrok "Trojan:Win32/Kepavll!rfn"`；该轮搜索没有取得针对同一检测的可核实修复结论。
- 官方FAQ明确提供二进制签名与历史版本哈希核验入口；随后打开归档源码中的SHA256字段，复核本机ZIP得到一致结果。初次只提取可见文字未读到input字段，不能据此判定哈希缺失。
- 已确认：ZIP对应官方3.39.11 Windows amd64，SHA256 `699bbf1932ec43a573b764bd03e6568efa2c4e45955eb3cc2089c19bb4be4464`。
- 未确认：提取EXE的Authenticode签名、此次检测是否误报、安全厂商是否已修正、客户端能否启动及手机公网可达。
- 建议处理：核对并通过系统正常渠道更新Defender安全情报；向微软提交疑似误报分析，并提供已核验版本/哈希给ngrok核实。取得针对该检测的可信处理结果后再验证客户端及HTTPS。此处是待执行路线，不表示已更新、提交或解除隔离。
- 微软文档亦列出企业允许指标/排除等临时缓解方法；本项目未核实当前检测，不采用放宽防护作为交付捷径。
- Authtoken尚未配置是独立待办：只处理本机所需的单项凭据；此前整页导出拒绝不等于ngrok功能故障。

## 验收与约束

后续未知阻碍记录必须包含至少一个已阅读的相关来源及适用性判断；无法联网或未找到匹配答案时如实写明，不伪造来源。修改后必须验证原错误是否消失及关键回归；“查到办法”“来源核验通过”“问题解决”“可交付”分开登记。
